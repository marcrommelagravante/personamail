# PersonaMail Database Design

## Ownership model

Every application record belongs to the authenticated user. Routers must filter
by `user_id` so an ID supplied by a browser can never grant access to another
user’s records.

## Tables

| Table | Purpose | Key relationships |
| --- | --- | --- |
| `users` | Google-authenticated PersonaMail accounts | Primary key: `id`; unique `email` |
| `contacts` | Per-person communication profile | `user_id → users.id` |
| `templates` | Reusable email drafts | `user_id → users.id` |
| `activities` | Compose, Improve, and Review history | `user_id → users.id`; optional `contact_id → contacts.id` |
| `user_preferences` | Defaults for new contact profiles | `user_id → users.id` (one-to-one) |

### `contacts`

Stores the relationship, tone, greeting, closing, and notes used to personalize
AI output. `name`, `relationship`, and `tone` are required.

### `templates`

Stores a named email subject/body plus optional relationship and tone guidance.
Templates are private to their owner.

### `activities`

Stores the request and output of completed Compose, Improve, and Review actions.
Email actions include a subject; Review stores a summary instead. History items
can be deleted by their owner.

### `user_preferences`

One record per user. It supplies the default tone, greeting, and closing when a
new contact profile is created.

## Migrations

Use Git Bash from `backend/`:

```bash
source venv/Scripts/activate
alembic revision --autogenerate -m "describe change"
# Review the generated file in alembic/versions/ before applying it.
alembic upgrade head
alembic check
alembic current
```

The existing Neon database is stamped at `20260809_0001`. A new, empty database
uses `alembic upgrade head`; do not run `alembic upgrade` against an unreviewed
autogenerated migration.

## Data handling

History can contain email text. Keep `DATABASE_URL` secret, restrict database
access to trusted environments, and do not log request bodies, OAuth tokens, or
AI output containing user content.
